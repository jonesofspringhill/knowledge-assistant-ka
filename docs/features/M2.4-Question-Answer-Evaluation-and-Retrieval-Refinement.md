# M2.4 Question-Answer Evaluation and Retrieval Refinement

**Identifier:** M2.4  
**Status:** Implemented; clean baseline and human acceptance review pending  
**Related milestone:** M2 - Local Question Answering and Retrieval Improvement  
**Depends on:** M1 Retrieval Foundation and M2.3 Grounded Single-Question Answering  
**Related decisions:** ADR-002, ADR-004  
**Version:** 1.0  
**Date:** 2026-08-24

---

## Purpose

Measure the reliability of the complete local question-answer pipeline and make
only those retrieval, context, or prompt refinements justified by recorded
evaluation evidence.

M1 already evaluates ranked retrieval. M2.3 already supplies one bounded,
grounded answer with structured citations and abstention. M2.4 adds a separate,
reproducible QA evaluation capability covering:

```text
Question -> Retrieval -> Context -> Local LLM -> Answer and citations
```

The feature establishes a versioned benchmark, records an immutable baseline,
applies fixed quality gates, supports repeatable human review where semantic
judgement is unavoidable, and compares candidate runs without changing the
meaning of the existing M1 `evaluate` command.

## Scope

M2.4 includes:

- a committed, versioned QA benchmark using shareable synthetic or public test
  material;
- support for separate local benchmarks against private workspaces;
- strict benchmark validation before model invocation;
- one full QA invocation per benchmark case and repeat;
- capture of the exact retrieved evidence used by the QA invocation;
- automatic retrieval, source, citation, abstention, and latency metrics;
- a deterministic human-review template and scoring rubric for semantic
  measures;
- persistent JSON and Markdown evaluation artefacts;
- immutable baseline designation and candidate comparison;
- fixed quality and regression gates defined before tuning;
- an explicit QA evaluation CLI separate from M1 retrieval evaluation;
- evidence-led refinement of retrieval settings, context selection, or the
  question-answer prompt when the baseline identifies a specific weakness;
- regression protection for M1 retrieval and M2.3 answer contracts;
- documentation of the final measured results and any accepted trade-offs.

---

## Out of Scope

The following do not block M2.4:

- replacing the existing M1 retrieval evaluation command;
- an LLM-as-judge service;
- cloud-hosted evaluation or telemetry;
- automatic prompt search or autonomous hyperparameter tuning;
- training or fine-tuning an embedding or language model;
- evaluating conversation memory or multi-turn behaviour;
- agents, tools, planning, or external actions;
- general contradiction detection beyond benchmark cases with supplied
  conflicting evidence;
- formal medical or legal validation of source content;
- guaranteeing identical generated wording between runs;
- parallel model execution or GPU optimisation;
- a graphical evaluation dashboard;
- publishing private questions, answers, source text, or workspace reports;
- making every possible retrieval enhancement listed in the roadmap.

## Evaluation Boundary

### Existing M1 retrieval evaluation

The existing command remains:

```text
knowledge-assistant evaluate <retrieval-benchmark.json>
```

It evaluates retrieval only and retains its current schema and metric meanings,
including Recall@K, MRR, similarity, index size, and retrieval latency.

M2.4 shall not silently add generation, semantic answer scoring, or different
threshold semantics to that command.

### New M2.4 QA evaluation

M2.4 evaluates the public M2.3 question-answer service, rather than reproducing
its pipeline logic:

```text
Validated QA case
       |
       v
answer_question(...)
       |
       +---- captured ranked retrieval results
       |
       v
QuestionAnswerResult
       |
       v
automatic checks + review template + persistent report
```

The evaluator shall not perform one retrieval for metrics and a second
retrieval for generation. Metrics must describe the same ranked result set used
by the answer invocation. The evaluator may inject a recording wrapper through
the existing QA service boundary to capture that single retrieval call.

## Benchmark Governance

### Two benchmark classes

1. **Repository acceptance benchmark**

   A committed benchmark of approximately 20-30 cases backed by small,
   shareable synthetic or public fixtures. It defines M2.4 regression gates and
   is safe for source control and CI.

2. **Local workspace benchmark**

   An optional benchmark for a real workspace such as `nutrition`. It may
   contain private questions, expected facts, and source identities. It shall
   remain in an ignored local-data or workspace-artifact location and is
   identified reproducibly by version and checksum rather than being committed.

The committed benchmark satisfies the milestone requirement for a fixed,
reviewable acceptance dataset. A local benchmark supplements it with realistic
operational evidence but shall never cause private material to be committed.

### Freeze rule

Before tuning begins:

- benchmark cases and fixtures shall be reviewed;
- the benchmark version and SHA-256 checksum shall be recorded;
- completion gates in this document shall be approved;
- a baseline run shall be written and marked as the baseline;
- no prompt, retrieval, context, or model setting shall be changed between
  benchmark approval and baseline capture.

After the baseline is recorded, changing a question, expected source, expected
fact, rubric, or gate requires a new benchmark version. Historical reports keep
their original benchmark identity.

### Privacy rule

Committed benchmark data shall contain no private document text, credentials,
absolute private paths, proprietary course extracts, or generated artefacts
from a private workspace.

Evaluation reports for private workspaces remain under ignored workspace
artefacts. Reports shall not include full retrieved context or rendered prompts
by default. They may retain the question, answer, stable logical source
identities, scores, citations, settings, and review results because those are
needed for diagnosis; the operator remains responsible for their local
handling.

## Benchmark Schema

The initial format is versioned JSON:

```json
{
  "schema_version": "1.0",
  "benchmark_id": "m2.4-qa-acceptance",
  "benchmark_version": "1.0.0",
  "description": "Grounded single-question QA acceptance benchmark",
  "cases": [
    {
      "id": "direct-001",
      "category": "direct_fact",
      "question": "What is the maximum community grant?",
      "answerability": "answerable",
      "expected_sources": [
        {"source_path": "documents/funding-guide.md"}
      ],
      "acceptable_sources": [],
      "expected_facts": [
        {
          "id": "grant-limit",
          "description": "The maximum grant is GBP 10,000"
        }
      ],
      "forbidden_claims": [
        "The grant is automatically awarded"
      ],
      "filters": {},
      "notes": "A direct fact with one preferred source."
    },
    {
      "id": "unanswerable-001",
      "category": "unanswerable",
      "question": "Who won the 2035 award?",
      "answerability": "unanswerable",
      "expected_sources": [],
      "acceptable_sources": [],
      "expected_facts": [],
      "forbidden_claims": [],
      "filters": {},
      "notes": "The corpus contains no future award result."
    }
  ]
}
```

### Required benchmark fields

The benchmark shall contain:

- `schema_version`;
- stable `benchmark_id`;
- semantic `benchmark_version`;
- non-empty description;
- between 20 and 30 cases for the repository acceptance benchmark;
- unique case identifiers without regard to letter case.

Each case shall contain:

- stable `id`;
- one category;
- non-empty question;
- `answerability`: `answerable`, `unanswerable`, or `conflicting`;
- zero or more expected source identities;
- zero or more acceptable alternative source identities;
- zero or more expected facts described for a human reviewer;
- zero or more forbidden claims;
- optional retrieval filters using the existing `KEY=VALUE` value model;
- optional review notes.

Source expectations shall prefer stable logical identity:

- `source_path`; or
- `document_id` where the benchmark deliberately pins it.

Generated chunk numbers shall not be required. Expected source filenames alone
are insufficient where multiple roots may contain the same name.

### Required category coverage

The committed benchmark shall include at least:

- 5 direct factual cases;
- 3 document-discovery or source-identification cases;
- 3 metadata-filtered cases;
- 2 temporal cases;
- 3 cross-document cases;
- 3 evidence-comparison cases;
- 3 deliberately unanswerable cases;
- 2 conflicting-evidence cases.

A case may satisfy more than one category concept, but it has one primary
category for reporting. The final set must total between 20 and 30 distinct
questions and contain at least 25 cases unless a documented fixture limitation
is approved before baseline capture.

## Reproducibility Record

Every run shall capture:

- evaluation schema version;
- unique run identifier;
- run kind: `baseline` or `candidate`;
- benchmark ID, version, checksum, and path;
- application version;
- Git commit when available and whether the worktree is dirty;
- workspace name and collection;
- Python and operating-system versions;
- embedding provider, model, and configured version;
- LLM provider and exact model identifier reported to the application;
- prompt name and checksum;
- retrieval `top_k`, threshold, filters, rerank flag, and cache policy;
- context maximum, reserved output, estimator identity, and effective budget;
- generation temperature, top-p, maximum tokens, and timeout;
- requested repeat count and repeat index;
- start and finish timestamps;
- retrieval, generation, and end-to-end latency;
- per-case result and aggregate metrics.

Secrets, environment tokens, raw full prompts, source document text, and raw
retrieved context shall not be written to reports.

A run with a dirty worktree is permitted for development but shall be visibly
marked. An accepted baseline or release comparison must use a clean worktree and
a resolvable commit identifier.

## Automatic Measures

### Retrieval measures

The QA report shall calculate from the single captured retrieval operation:

- Recall@5;
- Recall@10 where the effective `top_k` permits it;
- Mean Reciprocal Rank;
- expected-source presence in the context selected for generation;
- retrieval latency.

Expected and acceptable alternative sources both count as relevant. Results
must still report which class matched.

These QA-run retrieval values do not replace the separately pinned M1 retrieval
benchmark. The M1 benchmark shall also be rerun at each accepted candidate gate.

### Citation measures

The evaluator shall parse citation labels in the generated answer using the
M2.3 `[S<number>]` contract and calculate:

- **citation validity**: cited labels that resolve to evidence supplied in that
  invocation divided by all cited labels;
- **citation source correctness**: resolved citations whose source is expected
  or explicitly acceptable for the case divided by resolved citations where a
  source expectation exists;
- **citation presence**: answerable answers containing at least one resolved
  citation;
- invalid, duplicate, and unused supplied citation labels as diagnostics.

The CLI's displayed Sources list is not proof that the generated answer cited a
source. Metrics use labels actually present in the answer text.

Citation coverage of individual factual claims requires human review because a
string parser cannot reliably identify every substantive claim.

### Status and abstention measures

The evaluator shall calculate:

- answerable-case answer rate;
- unanswerable-case abstention accuracy;
- false-abstention rate on answerable cases;
- unsupported-answer rate on unanswerable cases;
- conflicting-case uncertainty presence;
- case completion and operational-failure counts.

`QuestionAnswerResult.status` is the authoritative structured status. Matching
particular prose such as "I do not know" shall not replace it.

### Latency measures

The report shall include:

- mean, median, and 95th-percentile retrieval latency;
- mean, median, and 95th-percentile generation latency;
- mean, median, and 95th-percentile end-to-end latency;
- per-case timings;
- model warm-up status when it can be determined.

Latency is diagnostic in the initial M2.4 gate because hardware differs. A
candidate shall nevertheless flag a regression greater than 25 percent against
the same-machine baseline when both runs have compatible pinned settings.

## Human Review Rubric

Semantic answer quality shall not be delegated to another LLM in M2.4. The
evaluation run creates a review template. A reviewer scores each completed
case using the benchmark expectations and only the evidence supplied to the
answer invocation.

### Per-case scores

#### Correctness: 0-4

- `4`: all expected key facts are correct; no material error;
- `3`: substantially correct with a minor omission or imprecision;
- `2`: partly correct but a material fact is missing or unclear;
- `1`: mostly incorrect or misleading;
- `0`: wholly incorrect, fabricated, or no usable answer to an answerable case.

#### Grounding: 0-4

- `4`: every substantive factual claim is supported by supplied evidence;
- `3`: one minor unsupported inference with no material effect;
- `2`: at least one material claim is only partly supported;
- `1`: several material claims are unsupported;
- `0`: answer is predominantly unsupported or contradicts supplied evidence.

#### Citation coverage: 0-4

- `4`: every substantive factual claim has an appropriate resolving citation;
- `3`: one minor claim lacks a citation;
- `2`: at least one material claim lacks an appropriate citation;
- `1`: citations cover little of the answer;
- `0`: no usable citations or citations do not support the claims.

#### Uncertainty/conflict handling: 0-4

- `4`: limitation or conflict is explicit, accurate, and not over-resolved;
- `3`: correct but could be clearer;
- `2`: limitation is incomplete or ambiguous;
- `1`: materially overconfident;
- `0`: invents resolution or answers an unanswerable case as fact.

The reviewer shall also record:

- IDs of satisfied and missed expected facts;
- any observed forbidden claim;
- count and short descriptions of unsupported material claims;
- `pass`, `fail`, or `needs_discussion`;
- an optional concise note.

Reviewer identity may be a local name or stable alias. Review timestamp and
rubric version are required. Changing a completed review shall preserve the
prior value in review history or create a new review file.

## Completion and Regression Gates

These gates are fixed before the first baseline and shall not be relaxed after
seeing results without a new specification version and an explicit recorded
decision.

### Structural gates

- 100 percent of generated citation labels resolve to supplied evidence;
- 100 percent of answerable answers contain at least one resolving citation;
- 100 percent of reports contain the required reproducibility fields;
- zero control-metadata records appear as factual evidence;
- zero operational case failures in an accepted run;
- zero critical unsupported claims, defined as a fabricated quantitative,
  safety, medical, legal, financial, or decision outcome.

### Automatic quality gates

- expected-source Recall@5 at least `0.90`;
- expected-source MRR at least `0.80`;
- expected or acceptable source present in generated context for at least
  `0.90` of answerable cases;
- unanswerable-case abstention accuracy at least `0.90`;
- false-abstention rate on answerable cases no greater than `0.10`;
- citation source correctness at least `0.95`;
- conflicting-case uncertainty present in every conflicting case.

### Human-review gates

- mean correctness at least `3.5 / 4` over answerable cases;
- no answerable case below `2 / 4` correctness;
- mean grounding at least `3.5 / 4`;
- mean citation coverage at least `3.5 / 4`;
- unsupported material claims in no more than `5 percent` of completed cases;
- every unanswerable and conflicting case scores at least `3 / 4` for
  uncertainty/conflict handling;
- no case marked `fail` remains without a documented disposition.

### Regression gates

- no accepted candidate reduces the separately pinned M1 Recall@5 or MRR by
  more than `0.02` absolute without an approved trade-off;
- no accepted candidate reduces an M2.4 automatic rate metric by more than
  `0.02` absolute;
- no accepted candidate reduces a mean human-review score by more than `0.10`;
- same-machine median end-to-end latency must not worsen by more than `25
  percent` unless the quality benefit and trade-off are recorded;
- structural gates may never be traded for higher average quality.

Passing the automated gates alone does not complete M2.4. Required human review
must be scored and included in the final aggregate report.

## Functional Requirements

### Benchmark validation

1. The application shall load QA benchmark JSON through strict typed models.
2. Unsupported schema versions, extra keys, duplicate case IDs, invalid
   categories, empty questions, invalid filters, and malformed expectations
   shall fail before retrieval or model invocation.
3. The repository acceptance benchmark shall contain 20-30 cases and meet the
   category coverage contract in this document.
4. Benchmark checksum shall be calculated from the exact input bytes.
5. Benchmark validation shall not require Ollama or a populated vector index.
6. A dedicated validation command shall print coverage counts, warnings, and
   benchmark identity.

### Execution

7. A QA evaluation run shall select one enabled workspace explicitly.
8. The evaluator shall reuse `answer_question` and shall not duplicate M2.3
   retrieval, context, prompt, citation, or abstention rules.
9. Each case/repeat shall invoke retrieval once and generation at most once.
10. If M2.3 abstains before generation, the evaluator shall record that no model
    invocation occurred.
11. Case filters shall be passed through the existing retrieval filter parser
    and search interface.
12. Cases shall run sequentially by default to avoid changing local-model
    resource and latency behaviour.
13. An optional positive repeat count may be used to observe variability; every
    repeat remains a distinct per-case record.
14. Default repeat count shall be one.
15. The run shall continue after a single operational case failure where safe,
    record the error without a traceback in normal output, and fail the run
    gate.
16. Keyboard interruption shall write a clearly marked partial report when at
    least one case has completed.
17. The evaluator shall never alter workspace configuration, prompts, source
    documents, embeddings, or the vector index.

### Result capture

18. Every case result shall retain structured M2.3 status, answer, uncertainty,
    supplied citations, citation labels found in the answer, captured ranked
    results, context-selected evidence identities, settings, and timings.
19. Reports shall retain stable logical provenance, not private absolute source
    paths.
20. Full evidence text and rendered prompts shall be excluded by default.
21. Automatic per-case measures shall be calculated deterministically from the
    case expectations and structured answer result.
22. Aggregate measures shall state their numerator, denominator, and any cases
    excluded as not applicable.
23. Empty denominators shall produce `not_applicable`, not a misleading zero or
    perfect score.
24. Percentiles and rate calculations shall be documented and covered by unit
    tests.

### Review and scoring

25. A completed run shall produce a separate review-template JSON file.
26. The template shall contain case identity, question, answer, supplied source
    identities, expectations, forbidden claims, and blank rubric fields.
27. It shall not contain raw source evidence or secrets.
28. A scoring command shall validate a completed review against its exact run
    ID, benchmark checksum, case IDs, and rubric version.
29. Missing required reviews shall be reported and shall prevent final gate
    success.
30. Scoring shall merge review measures into a new final report without
    overwriting the original raw run report or review input.
31. Automatic results shall not be editable through the review file.

### Reports and baselines

32. Each run shall write a unique, immutable JSON report and a concise Markdown
    summary beneath the selected workspace's evaluation artefacts.
33. A baseline designation shall identify an existing clean-worktree run; it
    shall not copy or rewrite its measured values.
34. There shall be at most one active baseline per benchmark ID and version in
    a workspace, while historical baseline records remain inspectable.
35. Candidate comparison shall require matching benchmark checksum and
    compatible workspace, prompt, model, and metric schema, or shall report the
    incompatibility explicitly.
36. A comparison shall show per-metric and per-case changes, regressions, fixed
    failures, new failures, setting differences, and gate outcome.
37. A mutable `latest` convenience reference may be written, but immutable run
    files are authoritative.
38. Report writing shall be atomic so a failed write does not replace the last
    valid artefact.

### Evidence-led refinement

39. No tuning shall begin before benchmark freeze and baseline designation.
40. Every proposed refinement shall name the baseline failure or weakness it is
    intended to address.
41. One logical variable group shall normally change per candidate: retrieval,
    context selection, prompt, or model/generation settings.
42. Configuration overrides used for an experiment shall apply only to that run
    unless a candidate is approved and deliberately incorporated into project
    configuration.
43. Query refinement, hybrid search, reranking, authority weighting, threshold
    changes, context-budget changes, and prompt changes remain optional; only
    measured needs justify implementation.
44. A refinement that changes a public contract or architectural boundary shall
    update the appropriate feature document or ADR before acceptance.
45. Accepted changes shall rerun the M1 benchmark, M2.4 benchmark, automated
    project suite, and interactive validation appropriate to the change.
46. A candidate failing a structural or regression gate shall not become the
    baseline.

### CLI and exit codes

47. QA evaluation shall use a new hierarchical `qa-evaluate` command and shall
    not alter the existing M1 `evaluate` command.
48. The CLI shall provide `qa-evaluate validate`, `run`, `review-template`,
    `score`, `baseline`, and `compare` actions.
49. Normal output shall show progress by case ID without printing full answers
    unless verbose output is requested.
50. Exit code `0` means the requested operation completed and all applicable
    gates passed.
51. Exit code `1` means evaluation completed or partially completed but one or
    more case operations, reviews, quality gates, or regression gates failed.
52. Exit code `2` means invalid CLI usage, configuration, benchmark, review, or
    incompatible comparison input prevented a valid evaluation operation.
53. Ollama/model unavailability during `run` shall be recorded as an operational
    failure and return `1`, with an actionable message.

## User Interface

### Validate a benchmark

```text
knowledge-assistant qa-evaluate validate benchmarks/qa/m2.4-acceptance-v1.json
```

Illustrative output:

```text
Benchmark: m2.4-qa-acceptance 1.0.0
Schema: 1.0
Cases: 25
Direct facts: 5
Document discovery: 3
Metadata filtered: 3
Temporal: 2
Cross document: 3
Evidence comparison: 4
Unanswerable: 3
Conflicting: 2
Checksum: 9f...
VALID
```

### Run a baseline candidate

```text
knowledge-assistant qa-evaluate run \
  benchmarks/qa/m2.4-acceptance-v1.json \
  --workspace evaluation \
  --kind baseline
```

The run remains a candidate for baseline designation until review is complete,
all applicable gates pass, and it is explicitly designated.

Illustrative output:

```text
Workspace: evaluation
Benchmark: m2.4-qa-acceptance 1.0.0 (25 cases)
Model: qwen3:8b
Prompt: question_answer 4b...

[1/25] direct-001       ANSWERED
[2/25] direct-002       ANSWERED
...
[25/25] conflict-002    ANSWERED

Automatic gates: FAIL (human review pending)
Run: .../evaluations/qa/m2.4-qa-acceptance/20260824T143012Z-a13f.json
Review template: .../20260824T143012Z-a13f.review.json
```

Pending human review is a gate failure, not an execution error.

### Score the review

```text
knowledge-assistant qa-evaluate score \
  workspaces/evaluation/artifacts/evaluations/qa/m2.4-qa-acceptance/20260824T143012Z-a13f.json \
  --reviews workspaces/evaluation/artifacts/evaluations/qa/m2.4-qa-acceptance/20260824T143012Z-a13f.review.json
```

The command writes a new `.scored.json` and `.scored.md` report and prints the
final gate outcome.

### Designate the accepted baseline

```text
knowledge-assistant qa-evaluate baseline \
  workspaces/evaluation/artifacts/evaluations/qa/m2.4-qa-acceptance/20260824T143012Z-a13f.scored.json
```

Designation shall fail if the run is unscored, from a dirty worktree, partial,
or incompatible with the benchmark identity. A gate-failing initial run may be
designated only with an explicit `--accept-failing` flag and non-empty recorded
reason. It remains a comparison baseline, not an accepted final result.

### Compare a candidate

```text
knowledge-assistant qa-evaluate compare \
  workspaces/evaluation/artifacts/evaluations/qa/m2.4-qa-acceptance/baseline.json \
  workspaces/evaluation/artifacts/evaluations/qa/m2.4-qa-acceptance/20260825T101500Z-b24f.scored.json
```

Illustrative summary:

```text
Metric                         Baseline   Candidate   Change   Gate
Recall@5                       0.92       0.96        +0.04    PASS
Citation validity             1.00       1.00         0.00    PASS
Abstention accuracy            1.00       1.00         0.00    PASS
Mean correctness              3.56       3.68        +0.12    PASS
Mean grounding                3.64       3.72        +0.08    PASS
Median end-to-end latency     12.4 s     13.1 s       +5.6%    PASS

Fixed cases: 2
Regressed cases: 0
Candidate: PASS
```

Exact presentation may differ, but the information and distinctions are
required.

## Error Handling

| Condition | Required behaviour | Recovery |
| --- | --- | --- |
| Unsupported benchmark schema | Stop before retrieval | Migrate or select a supported benchmark |
| Duplicate or malformed case | Identify case and field, then stop | Correct and revalidate benchmark |
| Workspace/index unavailable | Stop run with actionable message | Prepare or select the intended workspace |
| Ollama/model unavailable | Record operational failure; return `1` | Start Ollama or install/configure model, then rerun |
| One case invocation fails | Record failure and continue where safe | Diagnose the case and rerun a complete candidate |
| Run interrupted | Persist partial report when possible | Start a new complete run; partial cannot be baseline |
| Review missing or incomplete | Preserve raw run; fail final gates | Complete review template and score again |
| Review targets wrong run | Reject without modifying reports | Use the template generated for that run |
| Benchmark checksums differ | Reject comparison as incompatible | Compare runs from the same frozen benchmark |
| Dirty run proposed as baseline | Reject designation | Repeat from a clean committed state |
| Candidate misses regression gate | Retain report but reject as baseline | Revert or revise the candidate and rerun |
| Report write fails | Preserve existing files | Correct artefact storage and rerun |

Normal CLI output shall not expose raw tracebacks, full prompts, evidence text,
credentials, or secret environment values.

## Design Constraints

- Keep evaluation orchestration separate from question-answer generation.
- Reuse the public M2.3 answer service and M1 retrieval result contracts.
- Do not introduce a second retrieval implementation for evaluation.
- Keep benchmark models, evaluation result models, metric calculation, report
  persistence, CLI rendering, and human review as separate responsibilities.
- Make automatic metrics deterministic and independently unit-testable.
- Do not use generated prose matching as a substitute for structured status.
- Do not use another LLM as the source of truth for answer correctness.
- Preserve immutable raw measurements; scoring and comparisons create new
  artefacts.
- Keep settings explicit and recorded; evaluation shall not depend on hidden
  defaults.
- Keep the correct sequential CPU/local-model path even if later acceleration
  is added under ADR-004.
- Do not commit private benchmark or evaluation content.

## Acceptance Criteria

M2.4 is complete when:

- [x] This feature specification is approved.
- [ ] A 20-30 case shareable QA acceptance benchmark and its source fixtures are
  committed and versioned.
- [x] Benchmark validation covers schema, identity, category, filter, and source
  expectation rules.
- [x] `qa-evaluate` provides validate, run, review-template, score, baseline,
  and compare operations without changing M1 `evaluate` behaviour.
- [x] QA cases reuse one captured retrieval call through the M2.3 service.
- [x] Automatic retrieval, source, citation, abstention, conflict, completion,

## Interactive Validation Session

This session validates the operator workflow. It is not a replacement for the
automated suite or the scored benchmark review.

Commands use PowerShell from the repository root. Replace the evaluation
workspace name only if the committed acceptance fixtures define another name.

### 1. Close the remaining M2.3 operational check

Confirm the local model and intended real workspace are ready:

```powershell
knowledge-assistant doctor
knowledge-assistant workspace list
knowledge-assistant ask "Give one answer supported by the indexed workspace." --verbose
```

Expected observations:

- Ollama and the configured model are available;
- `ask` completes without a traceback;
- the answer either cites supplied evidence or returns structured insufficient
  evidence;
- verbose output identifies model, prompt checksum, retrieval settings, context
  budget, evidence count, and timings.

Record completion of the outstanding M2.3 interactive criterion in its feature
document or project journal before accepting the M2.4 baseline.

### 2. Validate the frozen acceptance benchmark

```powershell
knowledge-assistant qa-evaluate validate `
  benchmarks/qa/m2.4-acceptance-v1.json

$LASTEXITCODE
```

Expected observations:

- benchmark ID, version, checksum, 20-30 cases, and category counts are shown;
- validation does not invoke Ollama;
- the exit code is `0`.

### 3. Confirm M1 evaluation remains separate

Run the existing retrieval benchmark appropriate to the evaluation workspace:

```powershell
knowledge-assistant evaluate benchmarks/retrieval/m2.4-acceptance-v1.json
```

Expected observations:

- output contains retrieval metrics only;
- no LLM answers or QA review files are produced;
- results remain in the existing M1 evaluation location.

### 4. Run the QA baseline candidate

Start from a clean committed worktree and the prepared evaluation index:

```powershell
knowledge-assistant qa-evaluate run `
  benchmarks/qa/m2.4-acceptance-v1.json `
  --workspace evaluation `
  --kind baseline

$LASTEXITCODE
```

Expected observations:

- all cases run in stable case order;
- progress shows case identity and structured answer status;
- one raw JSON report, one Markdown summary, and one review template are written;
- settings and checksums are pinned;
- no source, index, prompt, or configuration file is changed;
- the run returns `1` while mandatory human review is pending.

### 5. Inspect privacy and citation diagnostics

Open the generated Markdown and JSON reports.

Expected observations:

- questions, answers, logical source identities, settings, and metrics are
  inspectable;
- full retrieved chunks and fully rendered prompts are absent;
- every answer citation label has a recorded resolution or explicit invalid
  status;
- no credential or private absolute source path is present.

### 6. Complete and score the human review

Fill each required rubric entry in the generated `.review.json`, then run:

```powershell
knowledge-assistant qa-evaluate score `
  <raw-run-report.json> `
  --reviews <completed-review.json>

$LASTEXITCODE
```

Expected observations:

- the review is accepted only for its exact run and benchmark checksum;
- a separate scored JSON and Markdown report is written;
- automatic and human metrics, failed cases, and all gate outcomes are shown;
- the raw run and review input are not overwritten;
- exit code is `0` only if every applicable gate passes.

### 7. Designate the baseline

If the scored run passes:

```powershell
knowledge-assistant qa-evaluate baseline <scored-run-report.json>
```

Expected observations:

- the designation records the immutable run ID and checksum;
- measured values are not copied or rewritten;
- a dirty, partial, unscored, or gate-failing run is rejected.

If the baseline does not pass, retain it as the measured pre-refinement baseline
and record that designation explicitly as a failing baseline. The implementation
may allow `--accept-failing` only with a required reason, because a
failing initial baseline may still be necessary for honest candidate comparison.
It may never be described as the final accepted M2.4 result.

### 8. Compare one justified candidate

Only if the baseline identifies a weakness, make or configure one scoped
refinement, run and review a candidate, then compare:

```powershell
knowledge-assistant qa-evaluate compare `
  <baseline-scored-report.json> `
  <candidate-scored-report.json>
```

Expected observations:

- setting differences are explicit;
- aggregate and per-case improvements and regressions are shown;
- the comparison applies the fixed structural, quality, and regression gates;
- a candidate cannot pass merely because one average improved while a
  structural gate failed.

### 9. Optionally validate the real private workspace

Run a separate, ignored local benchmark against `nutrition` or another real
workspace:

```powershell
knowledge-assistant qa-evaluate run `
  <ignored-local-benchmark.json> `
  --workspace nutrition `
  --kind candidate
```

Expected observations:

- the local benchmark is identified by version and checksum;
- its reports remain beneath ignored nutrition workspace artefacts;
- source paths in reports are logical root-qualified paths;
- nothing from the private benchmark or report is staged by Git.

## Automated Coverage Required

- strict benchmark and review schema validation;
- supported schema and rubric versions;
- case-insensitive case identity uniqueness;
- category coverage and case-count validation;
- benchmark byte checksum stability;
- filter validation before invocation;

  invalid labels;

- reproducibility and privacy field enforcement;
- atomic immutable report writing;
- review-to-run/checksum matching and incomplete review rejection;
- rubric aggregation and gate calculations;
- clean/dirty worktree baseline rules;
- compatible and incompatible comparisons;
- fixed-case and regressed-case reporting;
- M1 `evaluate` regression behaviour;
- CLI output and exit codes;
- end-to-end integration with synthetic documents and stubbed deterministic
  embedder/generator;
- optional real Ollama validation marked separately from the ordinary automated
  suite.

# M2.3 Grounded Single-Question Answering

**Identifier:** M2.3  
**Milestone:** M2 — Local Question Answering and Retrieval Improvement  
**Status:** Implemented
**Depends on:** M1 Retrieval Foundation, M2.1 Multi-Workspace Operations and Safe Refresh, M2.2 Evidence-Library Metadata Integration

---

## 1. Purpose

M2.3 introduces the first end-to-end local question-answering capability in the Knowledge Assistant.

The feature shall accept a single natural-language question, retrieve relevant evidence using the existing M1 retrieval subsystem, construct a bounded evidence context, invoke the configured local Ollama LLM, and return an answer grounded in the supplied evidence.

The feature must preserve provenance throughout the process so that the user can identify the evidence supporting the answer.

M2.3 is deliberately limited to **single-question grounded answering**.

It does not introduce conversational memory, autonomous agents, formal contradiction analysis, or unrestricted knowledge generation.

---

## 2. Architectural Principle

M2.3 shall reuse the retrieval capability already delivered by M1.

The processing path is:

```text
Question
   │
   ▼
Existing Retrieval Interface
   │
   ▼
Ranked Evidence + Provenance
   │
   ▼
Context Construction
   │
   ▼
Question-Answer Prompt
   │
   ▼
Configured Ollama LLM
   │
   ▼
Grounded Answer
   │
   ├── Citations
   └── Uncertainty / Abstention
```

M2.3 shall not:

- search source files independently;
- create an alternative vector search implementation;
- allow the LLM to choose arbitrary source documents;
- bypass workspace or metadata filters;
- discard retrieval provenance.

The M1/M2 boundary remains defined by `docs/decisions/002-m1-retrieval-boundary.md`.

---

## 3. Goals

M2.3 shall provide:

- a stable `knowledge-assistant ask` CLI command;
- grounded answers based on retrieved evidence;
- source citations;
- explicit insufficient-evidence handling;
- bounded and reproducible context construction;
- metadata-aware retrieval;
- diagnostic visibility into retrieval and generation;
- predictable local-model error handling;
- automated and interactive validation.

The primary measure of success is not fluency.

The primary measure is:

> Can the answer be traced to evidence that was actually retrieved and supplied to the model?

---

## 4. Scope

M2.3 includes:

- single-question CLI input;
- retrieval through the existing retrieval service;
- retrieval overrides;
- context selection and construction;
- prompt rendering;
- Ollama LLM invocation;
- answer generation;
- citations;
- uncertainty handling;
- abstention;
- operator-visible diagnostics;
- configuration;
- logging;
- unit tests;
- integration tests;
- interactive validation.

---

## 5. Out of Scope

M2.3 does not include:

- multi-turn conversational state;
- chat history;
- persistent user memory;
- autonomous follow-up questions;
- formal contradiction detection;
- agreement/disagreement classification;
- knowledge graph creation;
- agents;
- external tool execution;
- internet search;
- automatic source modification;
- automatic benchmark optimisation;
- M2.4 quality tuning.

Where retrieved evidence is contradictory, M2.3 shall report the conflict rather than formally classify it.

---

## 6. CLI Interface

M2.3 shall introduce:

```text
knowledge-assistant ask "<question>"
```

Example:

```text
knowledge-assistant ask "What funding limits apply to an Openwork Foundation grant?"
```

The question is a required positional argument.

---

### 6.1 Retrieval Options

The command shall support retrieval controls consistent with `search`:

```text
--top-k TOP_K
--threshold THRESHOLD
--filter KEY=VALUE
```

Multiple `--filter` options may be supplied.

Example:

```text
knowledge-assistant ask "What evidence is relevant to vitamin D?" \
  --top-k 8 \
  --threshold 0.35 \
  --filter role=student
```

---

### 6.2 Diagnostic Options

The feature should provide a diagnostic mode.

Preferred interface:

```text
--verbose
```

Verbose output shall make the effective execution state inspectable without requiring a debugger.

At minimum it should report:

- active workspace;
- active collection;
- selected LLM;
- embedding model;
- effective Top-K;
- effective threshold;
- effective metadata filters;
- number of retrieved results before context selection;
- number of evidence items supplied to the model;
- context budget;
- estimated context usage;
- generation latency;
- retrieval latency.

Verbose output may additionally include chunk identifiers and similarity scores.

Normal output shall remain concise.

---

## 7. Configuration

M2.3 shall use the existing configuration subsystem.

No model names, paths, thresholds or prompt filenames shall be hard-coded in the feature.

Required or expected configuration includes:

```yaml
llm:
  provider: ollama
  model: <installed-model-name>
  timeout_seconds: 120

retrieval:
  top_k: 5
  threshold: <configured-value>

question_answering:
  context:
    max_tokens: <value>
    reserved_output_tokens: <value>
  generation:
    temperature: <value>
```

Exact configuration structure may follow the existing repository conventions.

The specification does not require these precise YAML keys if equivalent validated configuration already exists.

---

### 7.1 Configuration Precedence

Effective values shall be resolved in this order:

```text
CLI override
   ↓
Workspace-specific configuration
   ↓
Global/default configuration
```

CLI overrides apply only to the current command invocation.

They shall not alter configuration files.

---

## 8. Retrieval Contract

M2.3 shall call the existing retrieval interface rather than duplicating search logic.

Each retrieved evidence item shall make available, directly or through structured metadata:

- chunk identifier;
- document identifier;
- workspace;
- chunk text;
- retrieval score;
- source filename;
- relative source path;
- source-root identity where relevant;
- document title where available;
- section title where available;
- page or source location where available;
- evidence metadata;
- checksum or equivalent source identity.

The exact internal retrieval model remains owned by the retrieval subsystem.

M2.3 shall consume it without unnecessarily redefining it.

---

### 8.1 Ordering

Retrieved evidence shall be presented to the context builder in retrieval rank order.

M2.3 shall not silently reorder evidence unless there is an explicit documented context-selection reason.

---

### 8.2 No Results

A retrieval returning no usable results is a valid outcome.

If no evidence survives:

- workspace isolation;
- metadata filters;
- similarity thresholding;

then M2.3 shall return an insufficient-evidence response without pretending that supporting evidence exists.

---

## 9. Filter Semantics

Filters shall use:

```text
KEY=VALUE
```

Example:

```text
--filter module=5
```

Unless an existing approved retrieval specification defines otherwise:

- multiple filters are combined using logical AND;
- malformed filters are rejected before retrieval;
- unsupported keys produce a clear error;
- empty keys or values are invalid;
- filters apply to the current invocation only.

M2.3 shall preserve the semantics already implemented by M2.2 metadata-aware retrieval.

It shall not introduce a separate filtering model.

---

## 10. Threshold Semantics

Threshold semantics shall be inherited from the M1 retrieval implementation.

The feature documentation shall state explicitly:

- the valid threshold range;
- whether higher values represent stronger matches;
- whether thresholding occurs before or after Top-K selection;
- what happens when all results are rejected.

The CLI shall display the effective threshold in verbose mode.

Similarity score shall not be presented as a universal confidence measure.

---

## 11. Context Builder

M2.3 shall introduce a dedicated context-construction component.

Its responsibility is to transform ranked evidence into a bounded, provenance-preserving context suitable for the configured model.

The context builder shall remain separate from:

- retrieval;
- prompt loading;
- Ollama invocation;
- CLI formatting.

---

### 11.1 Context Inputs

The context builder receives:

- user question;
- ranked evidence;
- evidence metadata;
- model/context configuration.

It outputs:

- selected evidence;
- rendered evidence context;
- provenance mapping;
- context-size diagnostics.

---

### 11.2 Context Budget

The context budget shall account for:

- system or instruction prompt;
- question-answer template;
- user question;
- evidence context;
- citation metadata;
- output token allowance.

The final model request shall remain within the supported context size of the selected model.

A reserved output allowance shall be maintained so that evidence does not consume the entire model context.

---

### 11.3 Token Counting

The implementation shall use one of:

1. an exact tokenizer suitable for the configured model; or
2. a conservative documented estimator.

Exact tokenisation is preferred where practical.

If an estimator is used:

- its method shall be documented;
- it shall err conservatively;
- diagnostics shall report that the value is estimated.

---

### 11.4 Evidence Selection

Evidence shall normally be considered in retrieval-rank order.

The context builder shall:

- preserve source provenance;
- prefer whole semantic chunks;
- remove exact duplicates;
- avoid unnecessary repeated overlapping text;
- preserve higher-ranked evidence before lower-ranked evidence.

Where the budget is exceeded, lower-ranked evidence should normally be excluded first.

---

### 11.5 Chunk Truncation

Whole-chunk inclusion or exclusion is preferred.

Arbitrary character-based truncation should be avoided.

If truncation is unavoidable:

- sentence boundaries shall be preserved where possible;
- provenance shall remain attached;
- the truncation shall be visible in diagnostics.

---

### 11.6 Adjacent or Overlapping Chunks

The implementation may merge adjacent or overlapping chunks where:

- they originate from the same document;
- ordering is known;
- duplication would otherwise waste context;
- provenance remains unambiguous.

Merging is optional for M2.3.

It shall not block completion if ranked evidence can already be supplied within budget.

---

## 12. Prompt Contract

M2.3 shall use the configured `question_answer` prompt through the existing PromptManager or equivalent prompt abstraction.

No prompt text shall be hard-coded in the model invocation layer.

The prompt shall provide the model with:

- the user's question;
- evidence context;
- source identifiers;
- instructions to answer only from supplied evidence;
- instructions to identify uncertainty;
- instructions not to fabricate missing facts;
- instructions to report conflicting evidence where relevant.

---

### 12.1 Required Prompt Behaviour

The prompt shall instruct the model to:

- use supplied evidence as the authoritative source;
- distinguish evidence from unsupported prior knowledge;
- avoid unsupported factual claims;
- cite supporting evidence;
- say when the available evidence is insufficient;
- avoid resolving conflicting evidence without support.

The prompt shall not encourage the model to fill gaps from general knowledge.

---

### 12.2 Prompt Variables

The M2.3 feature implementation shall define and test the required prompt variables.

At minimum they are expected to represent:

```text
question
context
```

Additional structured fields may include:

```text
sources
workspace
instructions
```

The exact variable names shall be documented in the feature implementation and prompt file.

Missing required variables shall produce a configuration or prompt-rendering error before LLM invocation.

---

## 13. LLM Integration

M2.3 shall invoke the configured local Ollama model through the project's LLM abstraction layer.

Direct Ollama calls shall not be introduced into CLI or retrieval modules.

The model name shall be obtained from validated configuration.

---

### 13.1 Model Availability

Before or during invocation, the application shall detect and report where practical:

- Ollama unreachable;
- configured model unavailable;
- invalid model name.

An unavailable configured model shall not silently fall back to a different model.

---

### 13.2 Generation Parameters

Generation parameters shall be configuration-controlled.

For M2.3, low-variance generation is preferred.

Where supported, configuration may include:

- temperature;
- maximum output tokens;
- timeout.

The exact parameters may vary according to the existing LLM abstraction.

---

### 13.3 Reproducibility

M2.3 does not require byte-identical answers across repeated model calls.

However, the following shall be identifiable for diagnostic and M2.4 purposes:

- model name/version;
- prompt version or checksum;
- effective retrieval settings;
- context settings;
- generation parameters.

---

## 14. Grounding

Grounding is a core M2.3 requirement.

A substantive factual claim is grounded when it can be supported by evidence supplied to the model for that invocation.

Model fluency, confidence wording or general plausibility shall not count as grounding.

---

### 14.1 Claim Support

The intended behaviour is that every substantive factual claim is supported by one or more cited evidence items.

The implementation does not need to perform full formal claim decomposition in M2.3.

M2.3 shall instead provide:

- a grounding-oriented prompt;
- source-labelled evidence context;
- citations in the answer;
- integration tests covering supported and unsupported questions.

Formal claim-level automated scoring belongs primarily to M2.4.

---

## 15. Insufficient Evidence

M2.3 shall explicitly distinguish lack of evidence from system failure.

Example response:

```text
The available evidence is insufficient to answer this question reliably.
```

This is a valid successful outcome.

---

### 15.1 No Retrieved Evidence

Where retrieval produces no usable evidence, the preferred behaviour is:

- do not invoke the LLM unnecessarily;
- return an application-generated insufficient-evidence response;
- report zero evidence in verbose diagnostics.

---

### 15.2 Partial Evidence

Where retrieved evidence addresses only part of the question, the answer should:

- answer the supported portion;
- state what cannot be established;
- cite the evidence used.

---

## 16. Conflicting Evidence

Formal contradiction analysis is outside M2.3.

However, M2.3 shall not hide obvious conflicting evidence.

Where the retrieved context contains materially differing statements, the answer should:

- state that the sources differ;
- summarise the relevant positions;
- cite each relevant source;
- avoid selecting one as correct unless the supplied evidence supports that conclusion.

Example:

```text
The available documents give different figures for the funding amount.
Source A states £10,000, while Source B states £15,000. The available
evidence does not establish which figure supersedes the other.
```

---

## 17. Citation Contract

Citations shall be derived only from evidence supplied to the model.

A citation must resolve to a retrievable source record.

At minimum, a normal user-facing citation shall identify:

- document title, if available;
- otherwise source filename.

Where available and useful it should additionally identify:

- section;
- page;
- source-root or relative path where disambiguation is required.

---

### 17.1 Fallback Citation Identity

Citation identity shall degrade gracefully.

Preferred order:

```text
Document title + section/page
↓
Document title
↓
Filename + section/page
↓
Filename
↓
Stable source identifier
```

Absence of document title shall not prevent citation.

---

### 17.2 Duplicate Filenames

If multiple source roots contain identically named files, citations shall contain sufficient root or relative-path information to distinguish them.

---

### 17.3 Paths

Normal user-facing answers should avoid displaying full absolute local filesystem paths.

Relative paths or logical source identities are preferred.

Absolute paths may be displayed in verbose diagnostic output.

---

### 17.4 Chunk Identifiers

Chunk identifiers are diagnostic metadata.

They need not appear in ordinary user-facing answers.

They should be available in verbose or machine-readable diagnostic output.

---

## 18. Output Format

Default output should be human-readable.

Conceptually:

```text
Question

<question>

Answer

<grounded response>

Sources

1. <source>
2. <source>

Uncertainty

<limitations where relevant>

Answer latency: <value>
```

The exact visual formatting may follow existing CLI conventions.

---

### 18.1 Uncertainty Section

The uncertainty section may be omitted where there is no material limitation.

It should be present where:

- evidence is incomplete;
- sources conflict;
- retrieval relevance is weak;
- only part of the question can be answered.

---

### 18.2 Machine-Readable Output

JSON output is not required for initial M2.3 completion unless an existing CLI convention already supports it.

The internal result model should nevertheless be structured so machine-readable output can be added later without redesigning the QA pipeline.

---

## 19. Internal Result Model

The implementation should expose a structured question-answer result rather than returning only formatted text.

Conceptually it should contain:

```text
question
answer
status
citations
evidence
uncertainty
retrieval_parameters
model
latency
```

Possible status values include:

```text
answered
insufficient_evidence
error
```

The exact class/model names are implementation decisions.

---

## 20. Error Handling

Expected operational failures shall produce concise actionable messages rather than unhandled tracebacks during normal CLI operation.

M2.3 shall handle at least the following cases.

---

### 20.1 Invalid Command Input

Examples:

- missing question;
- invalid Top-K;
- malformed threshold;
- malformed filter.

These shall be rejected before model invocation.

---

### 20.2 Configuration Failure

Examples:

- missing required prompt;
- invalid LLM configuration;
- invalid context configuration.

The command shall fail with an actionable error.

---

### 20.3 Ollama Unavailable

Example message:

```text
Unable to answer question: Ollama is not reachable at <configured-host>.
```

---

### 20.4 Model Missing

Example message:

```text
Unable to answer question: configured model 'qwen3:8b' is not available.
```

No automatic fallback shall occur.

---

### 20.5 Timeout

A model request exceeding the configured timeout shall terminate cleanly and report the timeout.

---

### 20.6 Empty or Malformed Model Output

An empty or unusable model response shall be treated as a generation failure.

It shall not be presented as an evidence-based answer.

---

### 20.7 Context Too Large

If the context builder cannot construct a valid request within the configured budget, the command shall fail with an actionable diagnostic rather than submit an invalid model request.

---

### 20.8 User Cancellation

Keyboard interruption should terminate cleanly without corrupting artefacts or workspace state.

---

## 21. Exit Codes

M2.3 shall define stable exit behaviour.

The preferred contract is:

```text
0  Successful answer
0  Successful insufficient-evidence result
2  CLI usage or validation error
1  Application/configuration/retrieval/model failure
```

If the project already defines different standard exit codes, M2.3 shall follow those existing conventions instead.

The chosen values shall be documented in `docs/features/CLI.md`.

---

## 22. Logging

M2.3 shall log sufficient execution information for diagnosis without logging unnecessary sensitive document content.

Logs should include:

- workspace;
- command type;
- model;
- retrieval parameters;
- result status;
- evidence count;
- timing;
- errors.

Full question or evidence text should only be logged where consistent with the existing logging/privacy policy.

---

## 23. Security and Privacy

M2.3 remains local-first.

The implementation shall:

- use the configured local Ollama service;
- not send source evidence to external cloud services unless a future explicit configuration allows it;
- preserve workspace boundaries;
- avoid exposing absolute local source paths in standard answer output;
- avoid writing full source context to logs by default.

---

## 24. Performance

M2.3 does not establish a strict latency SLA.

However, the implementation shall separately measure where practical:

- retrieval latency;
- context-construction latency;
- LLM generation latency;
- total answer latency.

These measurements provide the baseline for M2.4.

---

## 25. Automated Testing

M2.3 shall include unit and integration tests.

---

### 25.1 Retrieval Integration Tests

Verify that:

- the existing retrieval interface is called;
- Top-K is respected;
- threshold is respected;
- metadata filters propagate correctly;
- provenance is retained.

---

### 25.2 Context Builder Tests

Verify:

- ranked evidence remains ordered;
- duplicate evidence can be removed;
- context budget is respected;
- lower-ranked evidence is excluded first;
- provenance survives context selection;
- oversized evidence is handled predictably.

---

### 25.3 Prompt Tests

Verify:

- required variables render correctly;
- missing variables fail clearly;
- evidence/source labels appear in the rendered prompt;
- question text appears correctly.

---

### 25.4 Citation Tests

Verify:

- citations refer only to supplied evidence;
- missing titles fall back to filenames;
- duplicate filenames can be disambiguated;
- section/page metadata is used where available.

---

### 25.5 Insufficient-Evidence Tests

Verify:

- zero retrieval results return `insufficient_evidence`;
- the LLM need not be invoked in the zero-evidence case;
- command exit status is successful.

---

### 25.6 Failure Tests

Verify handling of:

- Ollama unavailable;
- model absent;
- timeout;
- empty model response;
- malformed filters;
- invalid context configuration.

Mocks/fakes may be used so tests do not require a live LLM unless explicitly marked as integration tests.

---

## 26. Interactive Validation

M2.3 shall be validated against at least one real workspace.

The validation set should include at minimum:

1. a direct factual question;
2. a question requiring evidence from a known document;
3. a metadata-filtered question;
4. a question with several plausible retrieved chunks;
5. an intentionally unanswerable question;
6. where available, a question exposing differing source statements.

For each test the reviewer should inspect:

- retrieved evidence;
- answer;
- citations;
- uncertainty;
- verbose diagnostics.

---

## 27. Example Validation Questions

The following are illustrative only and are not normative benchmark cases.

For a community/organisational workspace:

```text
What grants have been applied for?
```

```text
What amount of funding was requested in the sponsored grant application?
```

```text
Which documents discuss safeguarding?
```

For a nutrition evidence workspace:

```text
What role does vitamin D play in calcium regulation?
```

```text
Which module contains evidence about vitamin B12?
```

An unanswerable example should ask for a fact known not to be present in the test corpus.

## 29. M2.4 Handoff

M2.3 shall finish with a stable QA interface suitable for objective evaluation.

The handoff to M2.4 is:

```text
Question
   ↓
Retrieval
   ↓
Selected Context
   ↓
Prompt
   ↓
Model
   ↓
Structured QA Result
     ├── Answer
     ├── Evidence
     ├── Citations
     ├── Status
     ├── Uncertainty
     └── Diagnostics
```

M2.4 shall use this interface to evaluate retrieval and answer quality separately.

M2.3 shall not embed benchmark-specific logic into the runtime QA implementation.

M2.4 now implements this handoff through a recording search adapter around the
same answer service. The structured prompt contract includes an explicit
`Status: ANSWERED|INSUFFICIENT_EVIDENCE` field so model-selected abstention can
be measured even when retrieval returned evidence. Older model output without
the field remains backward-compatible and is treated as answered.

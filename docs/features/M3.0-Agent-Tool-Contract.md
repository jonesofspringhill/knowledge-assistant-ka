# M3.0 — Agent Tool Contract

**Status:** In progress

## Purpose

M3.0 makes Knowledge Assistant capabilities safely reusable by an external
agent, workflow engine, CLI wrapper, or another application. It is not an
agent loop and it does not grant an LLM direct access to documents, vector
stores, models, or external systems.

## Boundary

```text
Agent or workflow
        |
        v
Workspace-scoped tool contract
        |
        +-- knowledge.workspace.describe
        +-- knowledge.search
        +-- knowledge.ask
        |
        v
Existing KA services and evidence contracts
```

Every invocation supplies a `ToolContext` containing a workspace, caller and
run identifier. The registry enforces the caller's tool allow-list and rejects
write-effect tools unless write authority is explicit.

## Contract

Each registered tool publishes a JSON-serialisable descriptor containing:

- a stable dotted name;
- description and side-effect classification;
- workspace-scope requirement;
- Pydantic-generated JSON schemas for input and output.

Every invocation returns a `ToolResult` with its run ID, workspace, status,
structured result/error, warnings, and elapsed time. Inputs reject unknown
fields. Search and answer results retain source identity, citations, latency
and uncertainty.

## Initial Tool Set

| Tool | Effect | Purpose |
| --- | --- | --- |
| `knowledge.workspace.describe` | read-only | Describe the selected workspace and source roots. |
| `knowledge.search` | read-only | Return ranked, provenance-bearing evidence. |
| `knowledge.ask` | read-only | Produce a grounded answer with citations and uncertainty. |

Tools are inspectable with:

```powershell
ka tools list --json
ka tools describe knowledge.ask
```

They can be invoked by a process-oriented agent through JSON:

```powershell
ka tools invoke knowledge.search --workspace example --input '{"query":"What decisions were made?"}'
```

An invocation appends privacy-preserving metadata—never the arguments or
result—to `workspaces/<workspace>/artifacts/agent-tools/audit.jsonl`.

## Extension Rules

Custom tools must register a descriptor and validate their JSON input/output.
They must declare `read_only` or `write` effect. Write tools require explicit
authority and will be introduced only with user approval, dry-run support,
and a reviewable audit trail.

Tool implementations must be generic. Workspace names, organisation-specific
terms, paths, prompts and operating rules belong in local configuration or
workspace data, not in the core tool registry.

## Deferred Work

M3.0 deliberately does not yet include entity extraction, agent planning,
tool selection by an LLM, external tools, or autonomous writes. The next M3
increment will add a reviewed structured-extraction contract built on the same
workspace and evidence boundary.
